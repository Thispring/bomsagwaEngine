# 게임 엔진 제작 학습 로드맵

## 목표
- C++ 기본기를 학습하면서 게임 엔진에 필요한 자료구조/클래스 설계 경험 쌓기
- 부수적으로 렌더링 관련 공부를 하며 그래픽 추가
- 최종적으로 2D 기반 게임을 macOS/Windows/웹에서 배포 가능한 워크플로 구축

## 진행 원칙

### 학습 페이스
- 기간을 정해두고 몰아서 끝내는 방식이 아니라, **일주일에 최소 1회 이상은 반드시 이 프로젝트에 관한 학습/구현을 진행**한다.
- 바빠서 시간이 적은 주라도 완전히 손을 놓지 않고, 짧게라도 코드를 만지거나 개념을 정리하는 것을 원칙으로 한다.
- 각 Phase의 "기간"은 명시하지 않는다. 다음 단계로 넘어갈 준비가 되었는지는 아래 워터폴 검토 절차로 판단한다.

### 워터폴 방식 진행
- 각 Phase는 순차적으로 진행하되, 다음 Phase로 넘어가기 전에 **이전 Phase의 구현 사항을 반드시 검토(리뷰)**한다.
- 검토 시 확인할 것:
  1. 이전 Phase에서 만든 코드가 의도대로 동작하는가
  2. 설계상 아쉬운 부분이 있다면 다음 Phase로 넘어가기 전에 리팩토링할지, 일단 진행하며 기술 부채로 남길지 결정
  3. 이전 Phase에서 배운 개념이 다음 Phase에 어떻게 연결되는지 정리 (예: Time 매니저 → 게임 루프의 delta time)
- 다음 Phase 진행 중에도 이전 단계 구현을 계속 다듬는 것은 허용된다 (완전히 뒤로 돌아가지 않는 선에서 병행 개선).
- 즉, 순서는 지키되 각 단계가 "끝났다"고 완전히 종료 처리하지 않고, 프로젝트 전체를 계속 검토하며 누적 개선한다.

### 엔진 개발과 공부의 병행
- "공부만 하는 기간"과 "엔진을 만드는 기간"을 분리하지 않는다.
- 새로운 개념(자료구조, 렌더링 API 등)을 학습하면, 가능한 한 바로 엔진의 실제 구성 요소로 구현해 붙인다.
- 이렇게 하면 학습한 개념이 즉시 검증되고, 엔진도 꾸준히 발전한다.

## Phase 0: C++ 기초 + 핵심 자료구조 직접 구현
**목표**: 엔진 설계에 실제로 쓰이는 문법과 자료구조를 학습하며, 렌더링 없이 순수 C++ 실력을 다진다.

### 기초 문법
- 포인터/참조, RAII 개념
- 클래스, 상속, 가상 함수(vtable) 개념
- 템플릿 기초 (`vector<T>`, `unique_ptr<T>` 사용 수준)
- CMake 기초 (빌드 시스템 관리)

### 직접 구현할 것 (우선순위 순)
1. **UniquePtr 직접 구현**
   - 소유권 이전(move semantics), 복사 금지, RAII를 몸으로 체득하는 목적
2. **싱글턴 패턴 구현 → 이를 이용한 Time 매니저 구현**
   - 렌더링과 무관한 매니저 클래스부터 연습 (델타타임 계산은 Phase 1의 게임 루프에 바로 재사용됨)
3. **MyVector 직접 구현 (동적 배열)**
   - `new[]`/`delete[]`, 용량 증가 전략(예: 2배씩 growth), 복사/이동 생성자까지 구현
   - 메모리 관리 감각을 기르는 핵심 연습
4. **연결 리스트 간단 구현 (1회, 깊게 파지 않음)**
   - 포인터 조작 훈련 목적. 게임 엔진에서 `std::list`는 캐시 지역성이 나빠 실무에서 잘 쓰이지 않으므로 과도한 시간 투자는 지양
5. **map/해시맵은 구현 대신 원리 학습으로 대체**
   - 이진 탐색 트리의 O(log n) 원리, 밸런싱이 필요한 이유, 해시 충돌 개념 정도만 이해
   - 실제 레드-블랙 트리 구현은 난이도 대비 효율이 낮으므로 생략, 실전에서는 `std::map`/`std::unordered_map` 사용법 숙지로 대체
6. **string 클래스 (선택 사항)**
   - MyVector<char>와 구조가 유사해 중복 학습에 가까움. 여유 있을 때 Small String Optimization(SSO) 같은 심화 개념과 함께 시도

### 결과물
- 콘솔 프로그램 형태의 자료구조 구현체들 (UniquePtr, Time 매니저, MyVector 등)
- 이후 Phase에서 실제 엔진에 재사용

### 검토 포인트 (다음 Phase로 넘어가기 전)
- 구현한 UniquePtr/MyVector가 실제로 메모리 누수나 이중 해제 없이 동작하는지 테스트
- Time 매니저가 Phase 1의 게임 루프에 바로 통합 가능한 인터페이스로 되어 있는지 확인

## Phase 1: 창 띄우기 + SDL2로 첫 게임 루프
**목표**: Metal-cpp는 잠시 미뤄두고 SDL2로 "게임 루프" 개념 체득

```cpp
while (running) {
    HandleInput();
    Update(deltaTime);
    Render();
}
```

### 학습 항목
- SDL2 설치, 윈도우 띄우기, 사각형/텍스처 그리기
- delta time 기반 업데이트 (프레임 독립적 이동) — Phase 0에서 만든 Time 매니저 재사용
- 키보드 입력 처리

### 결과물
- 화면에서 방향키로 움직이는 사각형 프로그램

### 왜 SDL2부터인가
Metal-cpp로 바로 시작하면 셰이더, 파이프라인, 커맨드 버퍼 등 개념이 한꺼번에 쏟아져 게임 루프 자체를 배울 여유가 없음. 쉬운 도구로 게임 프로그래밍의 뼈대부터 잡는 것이 효율적.

### 검토 포인트
- 게임 루프가 프레임률에 관계없이 일정한 속도로 동작하는지 확인
- Phase 0의 자료구조(UniquePtr 등)를 게임 루프 내 리소스 관리에 실제로 적용했는지 점검

## Phase 2: 엔진 자료구조/클래스 설계 시작
**목표**: 본격적인 "엔진 만들기" 시작

### 학습 항목
- Entity 표현 방법 (처음엔 단순 클래스 상속으로 시작, ECS는 추후 리팩토링 가능)
- `Scene` / `GameObject` / `Component` 관계 설계
- `IRenderer` 인터페이스 설계 및 `SDL2Renderer` 구현
- 리소스 매니저 (텍스처 로딩/캐싱) — Phase 0의 싱글턴 패턴 재사용
- 간단한 이벤트 시스템

### 결과물
- 여러 오브젝트(플레이어, 적, 배경)가 각자의 클래스/컴포넌트로 관리되는 미니 데모

### 검토 포인트
- Phase 0~1에서 만든 요소들(Time 매니저, MyVector, IRenderer 등)이 실제로 엔진 구조 안에서 자연스럽게 맞물리는지 확인
- 설계상 무리가 있다면 이 시점에서 리팩토링 여부 결정

## Phase 3: 첫 미니 게임 완성
**목표**: 엔진이 아니라 "게임"을 완성해보는 경험

### 학습 항목
- 단순한 장르 선택 (퐁, 브레이크아웃, 플래피버드류 추천)
- 충돌 판정 (AABB 수준으로 충분)
- 점수, 게임 오버, 재시작 흐름
- 사운드 재생 (SDL_mixer)

### 결과물
- 처음부터 끝까지 플레이 가능한 완성작 1개

### 중요
엔진은 실제 게임을 만들어봐야 뭐가 필요한지 보인다. **엔진만 계속 만들다 게임을 하나도 완성 못 하는 함정을 피할 것.**

### 검토 포인트
- 완성된 게임을 플레이하며 엔진에서 부족했던 기능/불편했던 API를 목록화
- 이 목록을 다음 Phase 이후 엔진 개선 항목으로 반영

## Phase 5 (선택, 병렬 진행 가능): Metal-cpp / Vulkan 딥다이브
**목표**: 저수준 그래픽 학습 트랙

### 학습 항목
- 삼각형 그리기 → 텍스처 매핑 → 스프라이트 배치 렌더링
- `MetalRenderer : IRenderer` 구현 (기존 SDL2Renderer와 병행 존재)
- (선택) Vulkan + MoltenVK로 macOS/Windows 동시 대응하는 네이티브 렌더러 학습

### 비고
- 이 트랙은 기간 제약 없이 계속 진행 가능한 학습 트랙으로 둔다.
- 배포용 게임은 이미 SDL2 경로로 완성되어 있으므로, 이 Phase에서 실패하거나 오래 걸려도 프로젝트 전체 진행에 지장이 없다.
- Phase 1~4에서 이미 "렌더러가 뭘 해줘야 하는가"를 체득했기 때문에, 이 단계에서 저수준 API로 같은 기능을 구현하는 학습 효율이 높다.

## 참고: 엔진/게임 로직 분리 설계 (추후 확장용)

- 라이브러리 경계는 C ABI로 (C++ vtable/name mangling/STL 버전 문제 회피)
- `extern "C"`로 `Create/Destroy` 함수 쌍 노출
- macOS: `.dylib`, Windows: `.dll`, Linux: `.so`
- `dlopen`/`LoadLibraryA`로 런타임 로딩

## 참고: SDL2란?

- 윈도우 생성, 2D 렌더링, 입력, 오디오, 타이머 등을 플랫폼 무관하게 다룰 수 있게 해주는 C 라이브러리
- 게임 엔진이 아니라 게임 엔진을 만들 때 쓰는 저수준 도구 상자
- `Scene`, `GameObject` 같은 상위 개념은 SDL2 위에 직접 설계/구현해야 함

## 참고: SDL_Renderer의 크로스플랫폼 원리

- `SDL_Renderer`는 인터페이스, 실제 구현은 플랫폼별 "드라이버" (Metal/D3D11/OpenGLES2 등)
- 각 드라이버는 동일한 함수 포인터 테이블을 채워 넣는 방식 (C++ vtable과 동일한 원리)
- 빌드 시점에 타겟 플랫폼에 맞는 드라이버만 포함, 런타임에 우선순위대로 사용 가능한 드라이버 선택
- 각 드라이버 내부에는 이미 완성된 셰이더/파이프라인 코드가 플랫폼별로 미리 작성되어 있음

## 참고: Vulkan과 크로스플랫폼

- Vulkan은 개방형 표준 API로 Windows/Linux/Android에 네이티브 지원됨
- macOS/iOS는 Vulkan을 네이티브 지원하지 않으며, MoltenVK(Vulkan → Metal 변환 레이어)를 통해 사용 가능
- Vulkan + MoltenVK 조합은 macOS/Windows를 하나의 렌더링 코드로 커버할 수 있으나, 웹은 별도 대응(WebGPU/WebGL) 필요
- 따라서 웹 배포까지 포함하는 프로젝트에서는 SDL2 경로가 여전히 더 간단한 크로스플랫폼 해법
